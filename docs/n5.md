# N5

`icechunk-n5` lets N5 read and write an [icechunk](https://icechunk.io) repository. It provides
`IcechunkKeyValueAccess`, an N5 `KeyValueAccess` over an icechunk session, so n5-zarr's Zarr v3 reader and writer
work on a repository the same way they work on a directory or a bucket. This page covers what icechunk adds to a
Zarr v3 container, how to open one from code, and what does not work yet.

!!! warning "Experimental"
    The API will change, and no N5 tool can open a repository from a URL yet
    ([What is missing](#what-is-missing)).

## icechunk in N5 terms

An icechunk repository holds a Zarr v3 hierarchy, with version control on top:

- A **snapshot** is one committed version of the whole hierarchy, with an id such as `8AFVAQM5BQKKPY0GFGPG`.
- A **branch** names the latest snapshot of a line of work, as in git. A **tag** names a fixed snapshot.
- A **session** reads one version, or collects writes on a branch. Nothing a session writes is visible to anyone
  else until you **commit** it, which makes a new snapshot in one atomic step. A commit that loses a race with
  another writer on the same branch fails with `ConflictException`, and the repository is unchanged.
- Each session has a **store** (`session.store()`): the Zarr key/value view of that session, which
  `IcechunkKeyValueAccess` reads and writes.

N5 sees a session as a container. Every N5 reader or writer here is built on one session, so it reads one version, and
a writer's chunks become a snapshot only when the session commits. Data written this way is ordinary Zarr v3:
icechunk-python and zarr-python read it, including gzip-compressed and sharded datasets.

## Get the jars

Nothing is on Maven Central or the SciJava repository yet, so build from source and install the jars into your local
Maven repository. You need [pixi](https://pixi.sh), which provides JDK 21 and Maven, and
[rustup](https://rustup.rs).

In a clone of icechunk-java:

```sh
pixi run build-native
pixi run mvn -B install -DskipTests -pl icechunk-java,icechunk-n5 -am
```

Then depend on `icechunk-n5`. It declares n5 as `provided` and does not bring in n5-zarr or n5-universe, so add the
versions you use, from the [SciJava Maven repository](https://maven.scijava.org/content/groups/public) if your
project does not already list it. icechunk-n5 is built against n5 4.0.2, n5-zarr 2.0.2 and n5-universe 3.1.0.

```xml
<dependency>
  <groupId>io.earthmover.icechunk</groupId>
  <artifactId>icechunk-n5</artifactId>
  <version>0.1.0-SNAPSHOT</version>
</dependency>
```

The jars target Java 8, like n5-universe and n5-ij. A source build does not bundle the native library, so point the
JVM at it with `-Dicechunk.native.dir=/path/to/icechunk-java/native/target/debug`.

The samples below are sections of `examples/src/main/java/io/earthmover/icechunk/examples/N5Basics.java`, which
runs with `pixi run example N5Basics`.

## Open a repository

A repository lives in a `Storage`: a local directory, memory, S3, Google Cloud Storage, Azure, or HTTP for
read-only access.

```java
--8<-- "N5Basics.java:repository"
```

`Repository.open` opens an existing one, and `Repository.openOrCreate` does either.

## Write and commit

Open a writable session on a branch, build an n5-zarr writer on it, write, and commit:

```java
--8<-- "N5Basics.java:write"
```

The base path is `""`: paths are relative to the repository root. After `commit` the session is read-only, so open a
new one for more changes, or keep one writer across commits as in
[Keep a writer across commits](#keep-a-writer-across-commits). Writes that are never committed never reach a
snapshot, and `session.discardChanges()` drops them from the session.

## Read a version

A read-only session opens the tip of a branch, a tag, a snapshot, or a branch as it was at a point in time. Two
readers on two sessions see two versions of the same chunk:

```java
--8<-- "N5Basics.java:read"
```

The sample uses `Version.branch` and `Version.snapshot`. The other two kinds are `Version.tag("v1")` and
`Version.asOf("main", instant)`. A session on `Version.branch("main")` stays on the snapshot that was the tip when it
opened; open a new session to see later commits.

## Open through n5-universe

`N5Factory` opens readers and writers over the same object. Pass `StorageFormat.ZARR3`: icechunk holds Zarr v3 only.

```java
--8<-- "N5Basics.java:universe"
```

`IcechunkKeyValueAccess` ignores the URI's scheme and authority, so `URI.create("")`, `/` and `icechunk://anything`
all open the repository root. A caching factory such as `N5FactoryWithCache`, which Paintera's `PainteraN5Factory`
extends, caches by URI, so give each repository its own, such as `icechunk://<unique-id>`.

n5-universe logs `Compression 'org.janelia.saalfeldlab.n5.blosc.BloscCompression' could not be registered` when
n5-blosc's native library is missing. Other codecs are unaffected.

## numcodecs codecs

n5-zarr cannot decode arrays that zarr-python wrote with the `numcodecs.pcodec` or `numcodecs.zlib` codecs. Put the
`icechunk-n5-codecs` jar on the classpath and n5-zarr reads them, from icechunk or from any other store:

- `numcodecs.pcodec` replaces `bytes` as the array's serializer. It decodes `uint16`, `int16`, `uint32`, `int32`,
  `uint64`, `int64`, `float32` and `float64` arrays through the icechunk native library. Writing it is not supported.
- `numcodecs.zlib` is a compressor that stores each chunk as a zlib stream.

n5 finds codecs through a SciJava annotation index, which the jar carries, so no code needs to register them.

## Keep a writer across commits

An application that commits often, such as an editor that commits each edit, would otherwise rebuild its readers and
writers after every commit. `IcechunkKeyValueAccess` also takes a `Supplier<Store>`, which it asks for the store on
each operation, so the application can swap in a new session after each commit:

```java
--8<-- "N5Basics.java:swap"
```

A read that has already started keeps the store it started with, and fails if that session is closed before the
read finishes, so close the old session only once no reads on it are in flight. Between `commit` and the swap, the
supplier still returns the committed session, which is read-only, so a write from another thread in that window
throws. Commit and swap from one thread, and keep other writers out of that window.

## How icechunk differs from a file system

icechunk stores groups and arrays, not files and directories, so a few `KeyValueAccess` operations behave
differently:

- **Directories.** A path is a directory if it is the root or holds a `zarr.json`. `createDirectories` does nothing:
  a group or array exists once its `zarr.json` is written.
- **Node types are fixed.** Rewriting a group's `zarr.json` as an array's, or the reverse, fails.
- **Zarr v3 only.** icechunk accepts only Zarr v3 keys, so the N5 and Zarr v2 formats cannot write to it. Pass the
  format to n5-universe explicitly. When it guesses, it calls `exists(".zarray")`, which throws `N5IOException`
  instead of returning false, so the open fails.
- **Errors.** Errors from icechunk are thrown as `N5IOException`, with the `IcechunkException` as the cause.
  Writing through a read-only session is one of them. Reading or writing a path that is not a key icechunk can hold,
  such as a group's path, throws `IllegalArgumentException`.

## What is missing

- **Opening from a URL.** An N5 tool that opens containers from a URL, such as n5-ij's dialogs, cannot open a
  repository yet. That needs a way for n5-universe to map a URL such as `s3://bucket/repo` plus a branch, tag or
  snapshot to an `IcechunkKeyValueAccess`. A `KeyValueAccessProvider` service interface in n5-universe would do it,
  and a prototype exists, but it is not upstream.
- **Batched shard reads.** n5 reads the chunks of a shard one merged byte range at a time, each a separate call.
  icechunk can fetch many ranges in one call, but `IcechunkKeyValueAccess` does not use that yet.
- **Large writes.** Each write is copied twice on its way to icechunk, so peak heap is a few times the size of the
  largest shard.
